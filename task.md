# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: LIVE-СИНХРОНИЗАЦИЯ РЕЖИМОВ АВТОАТАКИ БОССОВ И ИНТУИТИВНАЯ РОТАЦИЯ В МЕНЮ БОССОВ

Ты выступаешь в роли Senior Full-Stack разработчика (Python / FastAPI / Asyncio + Vanilla JS / CSS) на проекте PrisonBot. Твоя задача - провести аудит текущей реализации очереди автоатаки боссов (бекенд, воркер, планировщик, фронтенд), гарантировать применение любых изменений режима, состава и приоритета боссов в реальном времени без перезапуска и лагов, а также внедрить интуитивно понятную визуализацию и управление стратегией ротации внутри модального окна «Меню боссов».

---

## 1. ЦЕЛЬ И БИЗНЕС-ТРЕБОВАНИЯ

### 1.1. Контекст и текущие проблемы
По текущему состоянию проекта (`workers/boss_worker.py`, `core/scheduler.py`, `core/state_hub.py`, `core/database.py`, `web/routes.py`, `web/static/app.js`, `web/static/index.html`, `web/static/styles.css`):
1. **Отставание или залипание настроек автоатаки боссов в рантайме**: при изменении режима атаки босса (`Пацанский` / `Блатной` / `Авторитетный`), состава очереди, лимита побед или приоритета в UI существует риск, что `boss_worker.py` продолжает использовать закэшированный снимок конфигурации, отложенное сохранение с фронтенда или старую очередь до окончания текущего цикла / рестарта.
2. **Непрозрачная система ротации в окне «Меню боссов»**:
   - На основной странице боссов уже выводится строка очереди вида `В очереди (6): Кирпич [Пац] -> Сизый [Авторитет] -> Махно [Авторитет] -> Лютый [Авторитет] -> Палыч [Пац] -> Воркута [Пац]`.
   - Внутри модального окна «Меню боссов» отображается только общий счетчик `В очереди: 6` и кнопки приоритета `▲` / `▼` на карточке босса.
   - При использовании поиска (например, ввод `лю` -> показан только `Лютый`) или фильтров категорий (`Беспредельщики`, `Надзиратели`, `Рецидивисты`) пользователь не видит ни текущую позицию босса в очереди, ни его соседей, ни результат нажатия `▲` / `▼`.

### 1.2. Бизнес-требования
1. **Мгновенное применение изменений (Live / Real-Time Config Reload)**:
   - Любое изменение в «Меню боссов» (переключение режима `Пацанский` / `Блатной` / `Авторитетный`, включение/выключение босса, изменение приоритета `▲` / `▼`, изменение дневного лимита, очистка очереди) должно немедленно сохраняться на бэкенде и становиться источником правды для воркера.
   - Воркер боссов перед **каждой новой атакой** обязан считывать актуальную конфигурацию очереди и режимов.
   - Если в момент изменения настроек бой с боссом уже идет в игре, активный бой корректно доводится до завершения/сбора награды, а **следующая атака** гарантированно выполняется строго по обновленным настройкам (новый режим, новый приоритет, актуальный список включенных боссов).
   - Если активного боя нет и воркер находится в режиме ожидания, изменение конфигурации должно немедленно пересчитывать план следующего запуска без ожидания долгого таймаута сна.
2. **Интуитивная визуализация и управление стратегией ротации в «Меню боссов»**:
   - Внутри модального окна «Меню боссов» должна отображаться живая панель текущей стратегии атаки (цепочка ротации), например: `#1 Кирпич [Пац] -> #2 Сизый [Авторитет] -> #3 Махно [Авторитет] -> #4 Лютый [Авторитет] -> #5 Палыч [Пац] -> #6 Воркута [Пац]`.
   - При повышении (`▲`) или понижении (`▼`) приоритета любого босса, смене его режима или включении/выключении панель стратегии должна обновляться мгновенно и наглядно подсвечивать перемещенный элемент.
   - На карточке каждого выбранного босса должен отображаться его актуальный порядковый номер в очереди (например, `#4`), чтобы позиция была понятна даже при активном поиске или фильтрации по категории.
   - Кнопки `▲` / `▼` должны переставлять босса строго относительно **глобальной очереди выбранных боссов**, а не только отфильтрованных в текущем поиске карточек.

## 2. КОНФИГУРАЦИЯ

### 2.1. Затрагиваемые модули и файлы
Перед началом правок агент обязан проинспектировать актуальный код следующих файлов в репозитории (в текущем контексте они не развернуты целиком):
- `workers/boss_worker.py` - цикл автоатаки боссов, выбор следующей цели, старт боя, обработка активного боя.
- `core/scheduler.py` - планирование тиков воркера боссов, механизмы wake-up / re-trigger при изменении настроек.
- `core/database.py` и `core/models.py` - схема хранения настроек боссов, порядка приоритета, режимов и лимитов.
- `core/state_hub.py` - публикация событий обновления состояния для UI и воркеров.
- `web/routes.py` - API-эндпоинты чтения и сохранения конфигурации очереди боссов.
- `web/static/index.html`, `web/static/app.js`, `web/static/styles.css` - модальное окно «Меню боссов», рендер карточек боссов, строка стратегии на основной странице и внутри модалки.
- `tests/test_boss_worker.py`, `tests/test_web_api.py`, `tests/test_realtime_scheduler.py`, `tests/test_state_hub.py` - существующие наборы тестов.

### 2.2. Контракт модели элемента очереди боссов
Убедиться, что структура конфигурации каждого босса в очереди (в БД, API и JS-состоянии) единая и детерминированная:

```json
{
  "boss_id": 4,
  "mode": "authority",
  "daily_limit": 7,
  "priority": 3
}
```

Правила нормализации:
- Позиция в очереди определяется либо порядком массива `queue` (индекс `0..N-1`), либо строго монотонно пронумерованным полем `priority` (синхронизированным с индексом в массиве). Если в проекте используется один из этих форматов - сохранить обратную совместимость с БД и API, но исключить рассинхронизацию между порядком массива и числовым приоритетом.
- Маппинг кратких меток режимов для строки стратегии (единый для главной панели и модального окна):
  - Пацанский -> `[Пац]`
  - Блатной -> `[Блат]`
  - Авторитетный -> `[Авторитет]`
- Ввести/проверить монотонный маркер версии конфигурации (например, `config_updated_at` или `boss_config_version` в `StateHub` / БД) для детекции изменений в рантайме и защиты от устаревших ответов (out-of-order HTTP responses).

## 3. ЛОГИКА / АРХИТЕКТУРА

### 3.1. Аудит и настройка Live-отслеживания настроек в бэкенде и воркере
1. **Устранение устаревшего кэша в `workers/boss_worker.py`**:
   - Проверить все места, где воркер читает список боссов для автоатаки, выбранный `mode`, `daily_limit` и порядок ротации.
   - Гарантировать, что конфигурация боссов **не кэшируется** в атрибутах инстанса или локальных переменных поверх нескольких атак.
   - Вынести чтение актуальной конфигурации в единый метод (например, `_load_fresh_boss_config()`), который вызывается:
     - в начале каждого тика воркера;
     - непосредственно перед выбором следующего босса для старта новой атаки (после завершения/сбора награды предыдущего боя или при переходе к следующей цели);
     - перед отправкой запроса старта боя в `client/api/boss.py` (контрольная сверка, что босс все еще в очереди, лимит не исчерпан и `mode` соответствует последнему сохраненному в БД).
2. **Поведение при изменении настроек во время активного боя**:
   - Если бой уже активен на сервере игры: воркер не ломает текущий бой и не сбрасывает его, а штатно доигрывает и забирает награду.
   - Сразу после завершения текущего боя (вместо повторного запуска того же босса со старым `mode` из памяти цикла) воркер перечитывает свежий список из БД:
     - если режим этого босса сменился (например, с `Пацанский` на `Авторитетный`), следующая атака на него пойдет строго в режиме `Авторитетный`;
     - если босса убрали из очереди, воркер переходит к следующему актуальному боссу;
     - если выше по приоритету появился другой доступный босс (хватает ключей и не достигнут дневной лимит), следующей целью выбирается он.
3. **Мгновенная реакция планировщика (`web/routes.py` -> `core/scheduler.py` / `core/state_hub.py`)**:
   - При сохранении настроек боссов через API в `web/routes.py`:
     - атомарно записать новые настройки в `core/database.py`;
     - обновить/опубликовать актуальный снимок состояния в `core/state_hub.py`;
     - если в `core/scheduler.py` есть механизм немедленного пробуждения / перепланирования задачи воркера боссов (wake-up event / `trigger_worker` / `reschedule`), вызывать его при изменении очереди или режимов (при включенной автоатаке), чтобы изменения не простаивали до следующего длинного тика.
   - Добавить явное структурированное логирование при каждом старте боя: `boss_id`, `boss_name`, `mode`, `queue_position`, `daily_wins/daily_limit`.

### 3.2. Немедленное сохранение без гонок на фронтенде (`web/static/app.js`)
1. Проверить, в какой момент сейчас отправляются изменения из модального окна «Меню боссов» на бэкенд:
   - Если сейчас изменения копятся в локальном черновике и отправляются только по кнопке «Готово» - перевести на **немедленное автосохранение (live sync)** при каждом действии пользователя (клик по режиму, чекбокс босса, кнопки `▲` / `▼`, изменение лимита с коротким debounce 250-300 мс, кнопка «Очистить очередь»), при этом кнопка «Готово» просто дожидается завершения активного запроса (если есть) и закрывает окно.
   - Если автосохранение уже есть - защитить его от **race conditions** (например, пользователь 3 раза быстро нажал `▲` или переключил режим и сразу закрыл окно):
     - использовать последовательную очередь сохранения (`saveInFlight` + флаг `pendingSave`, отправляющий всегда самый последний актуальный снапшот очереди) либо монотонный `requestSeq`, игнорирующий устаревшие ответы;
     - показывать ненавязчивый индикатор статуса синхронизации (например, `Сохранено` / `Сохранение...` в шапке или футере модального окна);
     - при ошибке сети/API откатывать оптимистичное изменение в UI и показывать понятное уведомление об ошибке.

### 3.3. Интуитивная система ротации и панель стратегии в «Меню боссов»
1. **Sticky-панель стратегии атаки внутри модального окна (`web/static/index.html`, `web/static/app.js`, `web/static/styles.css`)**:
   - Добавить в модальное окно «Меню боссов» (сразу под шапкой или под строкой поиска/фильтрами, в закрепленной области над скроллящимся списком карточек) блок **«Текущая стратегия атаки»** (или `Порядок ротации (N):`).
   - Вынести форматирование и рендеринг цепочки очереди в общую функцию в `web/static/app.js`, чтобы отображение внутри модалки и строка на основном экране боссов использовали единую логику и всегда совпадали.
   - Формат отображения внутри модального окна:
     - Горизонтальный flex-wrap (или компактный скроллируемый на узких экранах) ряд чипов, соединенных стрелками `->`:
       `#1 Кирпич [Пац]` `->` `#2 Сизый [Авторитет]` `->` `#3 Махно [Авторитет]` `->` ...
     - Каждый чип содержит:
       - порядковый номер `#1`, `#2`, ...;
       - имя босса;
       - визуально различимый тег режима (`Пац` / `Блат` / `Авторитет` с цветовым кодированием под активные кнопки режимов);
       - легкую интерактивность: клик по чипу фокусирует/прокручивает список к карточке этого босса (если босс скрыт текущим поиском или фильтром категории - очищает поиск и переключает фильтр на `Все`, затем плавно скроллит к карточке и на 1-1.5 секунды подсвечивает ее).
     - При пустой очереди выводить четкий текст: `Очередь пуста - выберите боссов для автоатаки`.
2. **Динамическая обратная связь при изменении приоритета (`▲` / `▼`)**:
   - На каждой карточке выбранного босса показывать бейдж его текущего номера в очереди (например, `#4 из 6` или компактный `#4`) рядом с кнопками `▲` / `▼`.
   - Логика кнопок `▲` и `▼`:
     - Работают строго по индексу босса в **полной очереди выбранных боссов**, независимо от примененного поиска (`лю`) или фильтра категории (`Беспредельщики` / `Надзиратели` / `Рецидивисты`).
     - Кнопка `▲` меняет босса местами с элементом `index - 1` (отключена `disabled`, если `index === 0`).
     - Кнопка `▼` меняет босса местами с элементом `index + 1` (отключена `disabled`, если `index === queue.length - 1`).
     - У невыбранных боссов кнопки `▲` / `▼` скрыты или заблокированы, чтобы не вводить пользователя в заблуждение.
     - Добавить понятные `title` / `aria-label` подсказки (`Повысить приоритет`, `Понизить приоритет`).
   - После каждого нажатия `▲` / `▼`:
     - Мгновенно перерисовывается панель стратегии в окне «Меню боссов» и строка стратегии на главной странице.
     - Перемещенный чип в панели стратегии получает краткий CSS-класс подсветки (например, `.strategy-chip--moved` на ~600 мс), чтобы глаз пользователя сразу фиксировал сдвиг в цепочке (например, `... -> Махно -> Лютый` стало `... -> Лютый -> Махно`).
     - Обновляется бейдж позиции `#N` на карточке босса и состояния `disabled` у кнопок `▲` / `▼`.
     - Запускается live-сохранение на бэкенд (см. п. 3.2).
3. **Адаптивность и визуальная целостность (`web/static/styles.css`)**:
   - Панель стратегии должна аккуратно выглядеть как на десктопе, так и на мобильных экранах: не ломать высоту модального окна, иметь ограниченную максимальную высоту с аккуратным вертикальным скроллом при очень длинной очереди (например, 10+ боссов), и соответствовать текущей темной палитре с золотым акцентом (`#eab308` / аналогичные CSS-переменные проекта).
   - Использовать существующие стили и иконки проекта без добавления лишних сторонних библиотек.

- [ ] 1. Провести аудит `workers/boss_worker.py`, `core/scheduler.py`, `core/database.py`, `core/state_hub.py`, `web/routes.py`, `web/static/app.js`, `web/static/index.html`, `web/static/styles.css` и зафиксировать все точки кэширования/задержки применения настроек боссов.
- [ ] 2. Реализовать/исправить обязательное перечитывание актуальной конфигурации очереди и режимов в `workers/boss_worker.py` перед каждой новой атакой (без ломки уже идущего боя) и добавить подробное логирование активного режима/позиции при старте боя.
- [ ] 3. Обеспечить мгновенное уведомление планировщика/воркера и `core/state_hub.py` при обновлении настроек боссов в `web/routes.py`, а также атомарность и нормализацию порядка приоритетов в `core/database.py`.
- [ ] 4. На фронтенде (`web/static/app.js`) реализовать защищенное от race-condition live-сохранение изменений (режим, чекбокс, приоритет `▲`/`▼`, лимит, очистка) с визуальным статусом синхронизации и откатом при ошибке.
- [ ] 5. Добавить в модальное окно «Меню боссов» (`web/static/index.html`, `web/static/app.js`, `web/static/styles.css`) динамическую панель текущей стратегии ротации (`#1 Босс [Режим] -> #2 ...`) с мгновенным обновлением, подсветкой перемещенного элемента, переходом по клику на чип и единой синхронизацией со строкой очереди на главной странице.
- [ ] 6. Улучшить карточки боссов в модальном окне: добавить бейдж текущей позиции `#N`, корректные состояния `disabled` и tooltips для кнопок `▲`/`▼`, работающих строго по глобальной очереди (в том числе при активном поиске/фильтре).
- [ ] 7. Написать и прогнать unit-/интеграционные тесты на live-смену режима, live-смену приоритета, удаление босса из очереди и API-сохранение.
- [ ] 8. Проверить синтаксис JS и прогнать полный прогон релевантных тестов `pytest`, убедиться в отсутствии регрессий.
