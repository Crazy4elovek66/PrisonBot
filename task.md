# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: ПОЛНЫЙ READ-ONLY АУДИТ VPS-СЕРВЕРА И ФОРМИРОВАНИЕ ОТЧЕТА VPS_AUDIT.MD

Ты выступаешь в роли Senior DevOps / Linux SRE инженера. Твоя задача - подключиться к продакшен VPS-серверу проекта PrisonBot в строго безопасном режиме **только для чтения (read-only)**, собрать исчерпывающий технический срез по железу, дискам, Docker-контейнерам (включая соседний конвейер вертикальных клипов), `systemd`-сервисам, веб-серверу/прокси, сети и текущему состоянию `/opt/prisonbot`, и сохранить детальный структурированный отчет в локальный файл `vps_audit.md`.

## 1. ЦЕЛЬ И БИЗНЕС-ТРЕБОВАНИЯ

Создать единый справочный документ `vps_audit.md` для дальнейшего архитектурного планирования (настройка долгоживущего кэша ассетов, автодеплой через GitHub Actions, изоляция ресурсов от конвейера вертикальных клипов и оптимизация стабильности):

1. **Строгий режим Read-Only на VPS**:
   - **ЗАПРЕЩЕНО** вносить любые изменения на сервере: ничего не устанавливать, не редактировать конфиги, не перезапускать `prisonbot.service` или Docker-контейнеры, не удалять файлы и не выполнять деплой кода в рамках этой задачи.
   - Все команды на сервере должны быть исключительно диагностическими и безопасными для работающего продакшена и конвейера видеоклипов.
2. **Строгая фильтрация секретов (Zero-Leak Policy)**:
   - В итоговый файл `vps_audit.md` **категорически запрещено** записывать пароли, SSH-приватные ключи, токены Telegram-ботов, API-ключи, `API_HASH`, строки сессий, куки, секреты вебхуков, пароли БД и любые реальные значения чувствительных переменных окружения.
   - Из `.env` / `docker-compose.yml` / `Environment=` в systemd можно выводить **только имена переменных** (ключи), заменяя все чувствительные значения на `[REDACTED]`.
3. **Полнота и конкретика**:
   - Все цифры (объемы дисков, RAM, CPU, размеры БД, контейнеров, порты, лимиты, пути) должны быть сняты с живого сервера, без догадок и заглушек.
   - Если для какой-то команды на сервере нет утилиты (например `iostat`), использовать доступные системные аналоги (`/proc/stat`, `vmstat`, `ps`, `ss`, `df`, `du`) и явно указать это в отчете.

## 3. ЛОГИКА / АРХИТЕКТУРА

Собрать на VPS данные по всем 7 блокам и оформить их в одноименных разделах файла `vps_audit.md`:

### 3.1. Железо, ОС и текущая утилизация ресурсов
- ОС и ядро: `cat /etc/os-release`, `uname -a`, `uptime`, часовой пояс (`timedatectl` / `date`).
- CPU: модель, число ядер/потоков (`lscpu` / `nproc`), текущий `Load Average`, топ-10 процессов по CPU (`ps aux --sort=-%cpu | head -n 15`).
- Память и Swap: `free -h`, `swapon --show`, проверка наличия OOM-killer событий в системном журнале (`dmesg -T | grep -iE "oom|killed process" | tail -n 20` или `journalctl -k | grep -i oom | tail -n 20`), топ-10 процессов по RAM (`ps aux --sort=-%mem | head -n 15`).
- Краткий замер дискового/CPU I/O: `vmstat 1 3` (для оценки `wa` / iowait под текущей нагрузкой).

### 3.2. Диски, разделы и карта занятого места
- Разделы и свободное место: `df -hT`, `df -ih` (свободные inodes - критично для кэша мелких спрайтов!), `lsblk -f`.
- Карта объема верхнего уровня (без обхода виртуальных ФС): `du -xh --max-depth=1 / /opt /var /home /srv /root 2>/dev/null | sort -hr`.
- Детализация по ключевым зонам:
  - Общий размер `/opt/prisonbot` и отдельно `storage/`, `storage/asset_cache/` (размер + количество файлов), `storage/prison_bot.db*` (`.db`, `-wal`, `-shm`).
  - Размер `/var/lib/docker` и директорий/volumes конвейера вертикальных клипов и остальных проектов.
  - Размер системных логов (`/var/log`, `journalctl --disk-usage`).

### 3.3. Docker-инфраструктура и соседние проекты (включая конвейер клипов)
- Версия Docker / Compose: `docker --version`, `docker compose version`.
- Полный список контейнеров (работающих и остановленных): `docker ps -a --format "table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}\t{{.RunningFor}}"`.
- Текущее потребление ресурсов контейнерами: `docker stats --no-stream`.
- Использование диска Docker: `docker system df -v` (образы, контейнеры, volumes, build cache).
- Конфигурация и изоляция каждого контейнера (`docker inspect` в сжатом структурированном виде):
  - Назначенные лимиты памяти (`Memory`), CPU (`NanoCpus` / `CpuQuota` / `CpusetCpus`), `RestartPolicy`, смонтированные `Mounts` (host path -> container path), сети (`Networks`).
  - Где на хосте лежат проекты контейнеров (`docker-compose.yml` / директории) - кратко описать роль каждого контейнера (особенно конвейера вертикальных клипов: чем рендерит, куда пишет временные и готовые файлы, есть ли очистка, есть ли лимиты на CPU/RAM).

### 3.4. Systemd-сервисы, фоновые задачи и планировщики
- Полное содержимое юнита `prisonbot.service` (`systemctl cat prisonbot.service`, со скрытием секретов) и его статус (`systemctl status prisonbot.service --no-pager`).
- Список всех остальных кастомных / пользовательских `systemd`-юнитов и активных сервисов (`systemctl list-units --type=service --state=running`, проверка `/etc/systemd/system/*.service`).
- Все задачи по расписанию: `crontab -l` (для текущего пользователя и `root`), `/etc/cron*`, `systemctl list-timers --all`.

### 3.5. Сеть, открытые порты, Reverse Proxy и SSL
- Все слушающие сокеты и процессы: `ss -tulpn`.
- Веб-сервер / Reverse Proxy (проверить `nginx`, `caddy`, `traefik`, `haproxy`, `apache2`):
  - Какие домены/поддомены и маршруты настроены (особенно для PrisonBot на `127.0.0.1:8085`).
  - Привести санитайзированные конфиги виртуальных хостов для PrisonBot (проверить `proxy_pass`, `proxy_read_timeout`, `gzip`/`brotli`, раздачу `/static/`, заголовки `Cache-Control`, SSL/Certbot).
- Firewall и сеть: статус `ufw status verbose` / `iptables -L -n` (кратко), скорость/доступность сети (опционально 1 легкий тест доступности GitHub `git ls-remote` / `curl -I https://github.com`).

### 3.6. Детальный аудит среды PrisonBot на VPS (`/opt/prisonbot`)
- Кто владелец файлов (`ls -la /opt/prisonbot`) и от какого пользователя работает `prisonbot.service`.
- Версия Python, расположение `venv` (`which python3`, `/opt/prisonbot/.../python --version`), установленные системные утилиты для будущих задач (`git`, `rsync`, `tar`, `sqlite3`, `curl`, `nginx`, `ffmpeg`, `docker`).
- Состояние Git в `/opt/prisonbot`: является ли папка git-репозиторием, настроен ли `remote`, есть ли SSH-ключи (`ls -la ~/.ssh`, **только имена файлов и права**, без содержимого приватных ключей!).
- Анализ базы данных `prison_bot.db` (read-only): размер, режим `PRAGMA journal_mode`, количество строк в основных таблицах (`notifications`, `action_logs` и др.).
- Последние 60-80 строк логов `journalctl -u prisonbot.service -n 80 --no-pager` (выделить наличие/отсутствие ошибок, предупреждений, таймаутов и перезапусков за последние сутки).

### 3.7. Инженерная сводка и рекомендации (для дальнейших задач)
В конце `vps_audit.md` сформировать краткую аналитическую таблицу/блок выводов:
- **Запас ресурсов**: сколько реально свободно CPU, RAM, диска (ГБ и inodes) с учетом пиков конвейера вертикальных клипов.
- **Риски соседства**: ограничены ли контейнеры видеоконвейера по CPU/RAM/IO, могут ли они забить диск или вызывать спайки пинга у PrisonBot.
- **Готовность к долгоживущему кэшу ассетов**: оптимальный путь на диске (например `/var/cache/prisonbot/assets` или внутри `/opt/prisonbot`), безопасный лимит объема, возможность прямой раздачи кэша через Nginx.
- **Готовность к автодеплою через GitHub Actions**: что уже есть (`git`, пользователь, права на `systemctl restart`), а что потребуется донастроить (Deploy Key, `sudoers` для рестарта или SSH-пользователь, защита `storage/*.db` и `.env`).
