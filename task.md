# ТЕХНИЧЕСКОЕ ЗАДАНИЕ: ЭНЕРГИЯ ХОДОК И МАСТЕРОВ, ФИКС СПИСКА ЗАЯВОК В ДРУЗЬЯ, РЕДИЗАЙН «НОВОСТИ И РЕЙДЫ» (ПАРСЕР @ITHEPRISON + ЕДИНЫЕ РЕЙДЫ И АВТО-ДРУЗЬЯ) И АУДИТ ВОРКЕРА ЗАРУБОВ + ДЕПЛОЙ НА VPS

Ты выступаешь в роли Senior Full-Stack разработчика (Python / FastAPI / Asyncio / Telethon + Vanilla JS / HTML / CSS) и специалиста по оптимизации веб-производительности на проекте PrisonBot. Твоя задача - реализовать четыре блока улучшений и исправлений (подсчет полной энергии круга в «Ходках и мастерах», устранение бага с пропаданием следующей заявки в друзья после одобрения, переработка раздела «Новости и рейды» с оптимизированным парсингом `https://t.me/itheprison` и объединенным поиском игроков с авто-рассылкой заявок, а также полный аудит и стабилизация воркера Зарубов), покрыть все изменения тестами и выгрузить релиз на VPS с проверкой в продакшене.

## 1. ЦЕЛЬ И БИЗНЕС-ТРЕБОВАНИЯ

### 1.1. Подсчет суммарной энергии на полный круг в «Ходках и мастерах»
- **Задача**: добавить расчет и отображение суммарной энергии, необходимой для прохождения полного круга (100% прогресса) по каждой зоне/тюрьме (отдельно для **дневного** и **ночного** режима) и по каждому **мастеру** (полный круг обучения/этапа).
- **Требования**:
  - На карточке каждой тюрьмы (днем и ночью) и каждого мастера должно быть четко видно, сколько энергии суммарно требуется на полный круг прохождения (с иконкой энергии `energy.webp` и точным числом).
  - Расчет должен опираться на реальные игровые формулы и данные API (с учетом количества дел/шагов и стоимости энергии каждого дела/действия, а также текущих бонусов/талантов, если сервер отдает итоговые цены шагов).
  - Если круг уже частично пройден, желательно дополнительно показывать (или в тултипе/подписи) остаток энергии до конца текущего круга рядом с полной стоимостью круга.

### 1.2. Исправление бага с пропаданием заявок в друзья после одобрения
- **Проблема**: при одобрении входящей заявки в друзья пропадает следующая заявка в списке. Например, если заявок две и принять одну - вторая исчезает из интерфейса до ручного или фонового обновления списка.
- **Требования**:
  - При одобрении (и отклонении) конкретной заявки из списка удаляется строго **только эта заявка** по ее уникальному ID.
  - Все остальные заявки в списке (включая единственную оставшуюся) обязаны мгновенно оставаться видимыми без перезагрузки/обновления списка.
  - Счетчик заявок должен точно уменьшаться на `1`, а локальное состояние фронтенда и кэш бэкенда (`core/state_hub.py`) должны оставаться строго синхронизированными без гонок при повторных кликах.

## 3. ЛОГИКА / АРХИТЕКТУРА

### 3.1. Расчет полной энергии на круг в «Ходках и мастерах»

   - Убедиться, что формула учитывает **реальный полный круг** (например, сумма `step_energy * total_steps_in_cycle` по всем обязательным делам тюрьмы отдельно для дневной и ночной смены; для мастера - полная энергия на полный цикл обучения).
2. **Backend (`client/api/prison.py`, `web/routes.py`)**:
   - Для каждой тюрьмы добавить явные поля в JSON-ответе API:
     ```json
     {
       "day_full_energy": 450,
       "day_remaining_energy": 120,
       "night_full_energy": 900,
       "night_remaining_energy": 900
     }
     ```
   - Для каждого мастера добавить аналогичные поля:
     ```json
     {
       "full_cycle_energy": 600,
       "remaining_cycle_energy": 240
     }
     ```
   - Не ломать существующие поля ответа и сохранить обратную совместимость с `workers/prison_worker.py`.

   - В карточке каждого мастера показывать суммарную энергию на полное обучение (`Полный круг: 600` + при наличии частичного прогресса `осталось 240`).

### 3.2. Исправление бага с пропаданием следующей заявки в друзья
1. **Диагностика первопричины**:
   - Проверить всю цепочку одобрения заявки в `web/static/app.js` (обработчик кнопки «Принять», оптимистичное обновление массива заявок, DOM-удаление и последующий `fetch`/ререндер) и на бэкенде в `web/routes.py` + `client/api/social.py` + `core/state_hub.py`.
   - Особо проверить:
     - не сравниваются ли разные поля идентификаторов (`req.id` vs `req.userId` vs `req.senderId` vs `req.vk_id` / `req.tg_id`) и не приводит ли `String(id)` / `undefined` к удалению соседней или всех заявок;
     - не затирает ли ответ после `accept` (или race condition с кэшем `StateHub` / повторным запросом) список входящих заявок пустым массивом;
     - не сбивается ли `page` / `offset` пагинации при принятии заявки (например, когда игровой сервер сдвигает индексы или возвращает неполную страницу).
2. **Исправление**:
   - Выделить нормализованный стабильный `request_key` для каждой заявки на бэкенде и фронтенде.
   - Удалять локально **только** принятую/отклоненную заявку по строгому совпадению `request_key`, обновлять счетчик точно на `-1`, блокировать кнопку конкретной заявки на время запроса (защита от двойного клика), а при синхронизации с бэкендом гарантировать, что актуальный список остальных заявок сохраняется целиком.
   - Инвалидировать домен друзей в `core/state_hub.py` корректно, не отдавая пустой промежуточный срез.

2. **Парсинг и рендер новостей `https://t.me/itheprison`**:
   - **Backend-сервис (`telegram/news_feed_service.py` + эндпоинты в `web/routes.py`)**:

       - основной быстрый и безопасный источник без риска FloodWait для личной сессии - асинхронный парсер публичной веб-версии `https://t.me/s/itheprison` (HTML + извлечение `tgme_widget_message`, форматирования `<b>`, `<i>`, `<code>`, `<blockquote>`, `<a href>`, фото `background-image`, GIF/видео `<video src>` и постеров, даты `datetime`, просмотров `tgme_widget_message_views`, `post_id` и прямой ссылки `https://t.me/itheprison/<id>`).

     - **Кэш ленты**: хранить распарсенные посты в памяти + SQLite/JSON с `NEWS_CACHE_TTL_SEC` и механизмом `stale-while-revalidate` (пользователю мгновенно отдается кэш, обновление идет фоново без блокировки ответа; ручная кнопка «Обновить» с троттлингом).

     - **Безопасность HTML**: строгий allowlist-санитайзер HTML на бэкенде (разрешены только `b`, `strong`, `i`, `em`, `u`, `s`, `code`, `pre`, `blockquote`, `br`, `a[href]`) + безопасный рендер на фронтенде (нулевой риск XSS).
   - **Frontend-оптимизация (`web/static/app.js`, `web/static/styles.css`)**:
     - Карточка поста в стиле Telegram Dark: медиа сверху (если есть), заголовок/текст с сохранением абзацев и эмодзи, блок цитаты `<blockquote>` с синей/акцентной левой полосой и иконкой кавычек справа сверху, нижняя строка с просмотрами, временем и ссылкой на оригинал.
     - Для GIF/видео:
       - рендерить `<video class="news-gif-video" loop muted playsinline preload="none" poster="..." data-src="...">` с бейджем `GIF` в углу;
       - на обычном/быстром соединении `IntersectionObserver` подгружает `src` и вызывает `play()` только когда пост в области видимости, и ставит на `pause()` при прокрутке мимо (экономия батареи, RAM и трафика);
       - на медленном соединении (`navigator.connection?.saveData === true` или `effectiveType` in `['slow-2g', '2g', '3g']`) показывать легкий `poster` + кнопку `▶ GIF` по тапу;
       - предусмотреть резервный обработчик `onerror` (если видео не декодировалось - аккуратно оставить постер с ссылкой на пост, без битых иконок).
     - Пагинация («Показать еще») и `aspect-ratio` контейнер для медиа (без дерганий страницы при догрузке).
3. **Вкладка «Рейды» - объединенный поиск игроков, сортировка и авто-рассылка заявок**:
