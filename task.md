## 1. ЦЕЛЬ И БИЗНЕС-ТРЕБОВАНИЯ

### 1.1. Игровая механика «Общак»
В игре «Тюряга» существуют 4 уровня месячной подписки «Общак» (дающей ежедневные награды и сохранение прогресса таланта после боя):
1. **Пацанский** (серебристая корона, 100 бумаги / 30 дней)
2. **Блатной** (золотая/бронзовая корона, 200 бумаги / 30 дней)
3. **Авторитетный** (красная корона с золотом, 500 бумаги / 30 дней)
4. **Воровской** (царская корона с золотыми лавровыми ветвями, 600 бумаги / 30 дней)

При просмотре профиля игрока в игре наличие общака отображается плашкой `ОБЩАК` с соответствующей короной под его ником.

### 1.2. Требования к функционалу входящих заявок в друзья
- Для каждой входящей заявки в друзья необходимо определить и вернуть:
  - наличие активного общака (`has_obshak: bool`);
  - точный тип/уровень общака (`obshak_tier`: `none` / `pacan` / `blat` / `avtoritet` / `vor` + числовой ранг `obshak_rank`: `0..4`);
  - человекочитаемое название (`obshak_label`: `Пацанский`, `Блатной`, `Авторитетный`, `Воровской` или пусто/отсутствует);
  - путь к стоковой иконке из игры (`obshak_icon`: `assets/icons/obshak_*.webp`);
  - опционально срок окончания/остаток дней, если игровой API его отдает для чужих игроков.
- В веб-интерфейсе в списке входящих заявок в друзья:
  - рядом с игроком отображать стильный бейдж с оригинальной стоковой иконкой общака из игры и подписью его типа (цветовое кодирование по уровню, чтобы владельцы `Воровского` / `Авторитетного` / `Блатного` / `Пацанского` общака сразу считывались глазами);
  - для заявок без общака показывать нейтральную приглушенную пометку (или не засорять карточку ярким бейджем) - главное, чтобы разница между «есть общак» и «нет общака» была мгновенно очевидна;
  - добавить компактную сортировку/фильтр для входящих заявок (например: «Все» / «Только с общаком» и сортировка «Сначала с высшим общаком» / «По умолчанию»), сохраняя при этом мгновенное одобрение/отклонение без бага пропадания следующей заявки (`getFriendRequestKey` / `syncFriendRequestRemoval`) и полную SSE-синхронизацию.
- **Производительность и защита от rate-limit**:
  - если игровой сервер отдает поле общака сразу в ответе списка заявок - использовать его напрямую без лишних HTTP-вызовов;
  - если игровой сервер отдает статус общака только в отдельном запросе профиля игрока (например, при «визите» / запросе профиля другого игрока) - реализовать быстрое кэшируемое дообогащение (in-memory кэш по `player_id` с TTL `15-30` минут, ограниченный пул параллельных запросов через `asyncio.Semaphore(3-4)`, мягкий таймаут и уважение `core/server_health.py`), чтобы список заявок открывался быстро и не спамил игровой сервер.

### 3.2. Backend-логика (`client/api/social.py`, `workers/social_worker.py`, `web/routes.py`)
1. **Единый парсер `parse_obshak_info(payload: dict, now_ts: Optional[float] = None) -> dict`**:
   - Принимает сырой объект заявки или профиля игрока, извлекает тип/уровень общака и проверяет активность (если есть срок окончания - сравнивает с `get_game_now_ts()`).
   - Возвращает стандартизированный словарь:
     ```python
     {
         "has_obshak": True,
         "obshak_tier": "vor",          # "none" | "pacan" | "blat" | "avtoritet" | "vor"
         "obshak_rank": 4,              # 0..4 (для надежной сортировки)
         "obshak_label": "Воровской",   # "" | "Пацанский" | "Блатной" | "Авторитетный" | "Воровской"
         "obshak_icon": "assets/icons/obshak_vor.webp",  # "" если нет
         "obshak_expires_ts": 1798502400,  # int | None (если сервер отдает)
     }
     ```
2. **Обогащение входящих заявок в `client/api/social.py`**:
   - Если данные общака присутствуют прямо в ответе списка заявок - распарсить мгновенно.
   - Если данные общака доступны только в эндпоинте профиля чужого игрока (как при открытии `Твин DS` / `ОСБ | Жандарм` в игре):
     - добавить кэш `_obshak_profile_cache: Dict[str, Tuple[float, Dict[str, Any]]]` с TTL (например `1800` сек) и ограничением размера (например `1000` записей);
     - реализовать `enrich_friend_requests_with_obshak(requests_list, max_concurrency=3, limit_fetch=25)` с защитой `asyncio.Semaphore`, обработкой ошибок (ошибка одного профиля не ломает весь список) и уважением `server_health_monitor`;
     - возвращать в каждом элементе списка входящих заявок поля `has_obshak`, `obshak_tier`, `obshak_rank`, `obshak_label`, `obshak_icon` (и `obshak_expires_ts` при наличии).
   - Убедиться, что поля общака сохраняются при записи в `core/state_hub.py` и при отправке через `GET` эндпоинты и SSE `social_updated`.
   - Если в списке текущих друзей или в ответе заявок есть те же поля без доп. запросов - аккуратно пробрасывать `parse_obshak_info` и туда, не увеличивая нагрузку на API.

### 3.3. Frontend-отображение (`web/static/index.html`, `web/static/app.js`, `web/static/styles.css`)
1. **Бейдж общака на карточке входящей заявки**:
   - Для игроков с активным общаком выводить аккуратный стилизованный бейдж `.obshak-badge.obshak-tier-{tier}` со стоковой иконкой `<img src="assets/icons/obshak_{tier}.webp" ...>` и названием уровня (`Пацанский`, `Блатной`, `Авторитетный`, `Воровской`):
     - `pacan` - стальной/серебристый акцент;
     - `blat` - теплый янтарный/золотистый акцент;
     - `avtoritet` - насыщенный рубиново-красный с золотой окантовкой;
     - `vor` - премиальный золотой/королевский акцент с легким свечением.
   - Для игроков без общака выводить компактную приглушенную метку `Без общака` (нейтральный серый, не перегружающий карточку).
   - Убедиться, что URL иконок корректно работают под subpath `/prison/` (относительный путь `assets/icons/...` или через `resolveAppUrl`, как у остальных иконок проекта).
2. **Фильтрация и сортировка входящих заявок**:
   - В шапке блока входящих заявок добавить компактный контрол:
     - фильтр `Все` / `С общаком` (со счетчиком заявок с общаком, если есть);
     - сортировка `Сначала с общаком` (по убыванию `obshak_rank`: `4 -> 3 -> 2 -> 1 -> 0`) / `По порядку`.
   - При одобрении или отклонении заявки (`syncFriendRequestRemoval`) и при SSE `applySocialUpdatedEvent` фильтр, сортировка и отображение оставшихся заявок должны оставаться полностью консистентными (не должно возникать исчезновения следующей заявки).
